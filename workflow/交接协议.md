# 交接协议 v1.0（团队包 0.1.2）

> 这份协议规定 11 个角色**怎么交接、怎么改状态、怎么找老板审批**。
> 状态和字段的定义在 `workflow/sku_states.yaml`；本文讲**动作和规矩**。
> 适用平台：StarSky（DSH）、OpenBot。两个平台的角色名对照见 `team.yaml`。

---

## 一、两层账本

```
┌──────────────── 全店 SKU 台账（运营总监管）────────────────┐
│ 一行一个 SKU：现在什么状态、归谁、各角色的结论、证据引用   │
│ → 所有角色看这里决定「该不该我干活」                       │
└───────────────┬─────────────────────────────────────────┘
                │ product_ref 指向
┌───────────────▼──── 产品文件夹（各技能的产物）──────────┐
│ 一个产品一份：S1–S5 各步骤的产物路径、hash、MCP 调用记录     │
│ → 专业技能照旧在这里干活，不用改                              │
└──────────────────────────────────────────────────────────┘
```

- **台账只记结论和引用**，详细过程留在产品根里。这样 平台 里原有的技能**不用改**，只是在外面多了一层「团队调度」。
- 两边对不上时，**以产品根里有证据的那一边为准**，由运营总监修正台账。

---

## 二、四条铁律

| # | 规则 | 怎么执行 |
|---|---|---|
| 1 | **单写者** | 台账每一列只有一个角色能写（见 sku_states.yaml 的 `fields`）。写别人的列，直接拒绝 |
| 2 | **按表走状态** | 只能从当前状态走到 `next` 里列出来的状态，不能跳步；进入新状态前，`requires` 里的字段必须已经填好 |
| 3 | **有证据才算数** | 每个结论都要有 `*_ref` 指向文件。**文件存在 ≠ 做完了**，要有验证结果。sha256 **由接收方收到文件后重算**，写入方不能在文件里写自己的 hash（先算后写，内容一变就失效） |
| 4 | **版本锁** | 写入时带上读取时的 `version`，对不上就拒绝写入，重新读一遍再做 |

## 三、交接信封（所有角色之间的消息都用这个格式）

```json
{
  "msg_id": "M-20261102-0042",
  "type": "TASK | RESULT | RETURN | GATE_REQUEST | GATE_DECISION | ESCALATE | HALT | INFO",
  "sku_id": "SC-2026-1102-001",
  "batch_id": "B-2026-1102-A",
  "from": "admin",
  "to": "guard",
  "from_status": "CANDIDATE",
  "to_status": "G1_PASS",
  "version": 3,
  "fields": {"g1_verdict": "PASS", "g1_ref": "S1_选品板块/amazon-ip-risk-assessment/04_ip_risk.md#sha256:9f2a..."},
  "summary_cn": "未发现商标和专利风险，不是受限类目",
  "idempotency_key": "SC-2026-1102-001:G1:v3",
  "created_at": "2026-11-02T10:20:00-08:00"
}
```

| type | 谁发 | 什么时候发 |
|---|---|---|
| `TASK` | 运营总监 → 角色 | 派活。附上要读哪些引用文件、截止时间 |
| `RESULT` | 角色 → 运营总监 | 做完了。附上要写入的字段 + 建议的下一个状态 |
| `RETURN` | 角色 → 运营总监 | 打回。必须写 `reason` 和 `fix_ref`（具体改什么） |
| `GATE_REQUEST` | 运营总监 → 老板 | 到闸门了，请老板决定 |
| `GATE_DECISION` | **只能是老板** → 运营总监 | 老板的批准 / 否决 / 修改 |
| `ESCALATE` | 任何角色 → 老板 | 打回超过上限、拿不准、超时 |
| `HALT` | 风控官 → 所有角色 | 账户健康碰到红线，全店暂停 |
| `INFO` | 任何角色 | 通知，不改变状态 |

**信封放哪里**：JSON 信封写进文件（比如 `消息/M-20261102-0042.json`），对话里只发对应的**中文交付卡** + 文件名。交付卡的格式见 `workflow/输出排版规范.md`。

**幂等**：同一个 `idempotency_key` 只处理一次。重发的消息直接忽略，避免重复上架、重复开广告。

## 四、运营总监的调度循环

```
每一轮（定时触发，或者收到消息时触发）：
1. 先看 halt_flag：如果已暂停 → 只派「只读」和「复盘」类的任务
2. 扫描台账，找出没进终态、也没在等老板的 SKU
3. 按 states[状态].owner 找到该干活的角色 → 发 TASK（一个 SKU 同一时间只能有一个未完成的 TASK）
4. 收到 RESULT：
   a. 检查发消息的人是不是这个状态的 owner
   b. 检查 to_status 在不在 next 列表里
   c. 检查 requires 字段是不是都填了，*_ref 文件是不是真的存在
   d. 检查 version
   e. 检查目标状态有没有被 HALT 挡住
   → 全部通过：写入台账，version + 1，prev_status = 原状态
   → 有任何一项不通过：退回给原角色，并说明是哪一项没通过
5. 新状态是 gate → 发 GATE_REQUEST 给老板（同一批次的合并成一张审批卡）
6. 超过 sla_h → 先提醒 owner；超过 2 倍时间 → ESCALATE 给老板
7. 每天输出一份「台账日报」（模板见第九节）
```

**运营总监不做专业判断**。它只检查流程对不对：是不是该你、跳没跳步、字段齐不齐、有没有证据。

## 五、打回规则

```
QA_CHECK ──✗──► CONTENT_WIP （质检官打回：写明是文案还是图片的问题）
G2_CHECK ──✗──► CONTENT_WIP （风控官打回：附 g2_fix_ref 修改清单）
PREVIEW  ──✗──► CONTENT_WIP （预检失败：附亚马逊返回的错误）
SUBMITTED──✗──► CONTENT_WIP （处理报告报错）
SOURCED  ──✗──► REJECTED    （风控官 G1b：实物图落入专利或版权）
IP_CLEARED──缺──► NEED_INPUT （财务管家缺数据 → 仓管物流补）
```

- 打回时 `return_count + 1`。**同一个环节打回超过 2 次 → 改成 ON_HOLD，交给老板**，免得 AI 一直在原地转圈
- 打回到 CONTENT_WIP 时，只重置有问题的那一边（比如只是图片有问题，`copy_status` 保持 done）
- 改过的内容**必须重新走 QA_CHECK → G2_CHECK**；图片改过的，**AI 人物标记要重新扫描、重新读回**

## 六、闸门审批

### 老板收到的审批卡（同一批次合并成一张）

```
🔒【闸门 1 · 选品确认】批次 B-2026-1102-A ｜ 待确认 8 个
┌────┬──────────────┬──────┬──────┬────────┬──────────┬──────────┐
│ #  │ 产品          │ 售价 │ 净利率│ 保本ACoS│ 建议方式  │ 风控条件  │
├────┼──────────────┼──────┼──────┼────────┼──────────┼──────────┤
│ 1  │ 硅胶收纳盒 3件 │$24.99│ 35%  │  35%   │ FBM 测款 │ —        │
│ 2  │ 桌面理线器     │$15.99│ 27%  │  27%   │ 只能 FBM │ 需 Prop65 │
└────┴──────────────┴──────┴──────┴────────┴──────────┴──────────┘
回复方式：「批准 1,3,5」「否决 2 原因：利润太薄」「全部批准」「搁置 4」
有风控条件的，必须单独回复「批准 2 并确认条件」才算通过
```

### 规矩
1. **只认老板本人**：StarSky 认老板在运营总监对话或团队群聊里亲自发的消息；OpenBot 认老板在运营总监对话里亲自发的消息。任何角色发出或转发的"批准"一律无效
2. **AI 不能替老板回复**，也不能把"老板没回复"当成同意
3. 老板修改的内容（比如「批准 3 预算改成 10」）写进 `approved_daily_budget` 等老板字段，`gateX_by` 和 `gateX_at` 自动记录
4. 老板超过 sla_h 没回复 → 提醒一次；再超时 → 保持原状态，不自动放行

## 七、HALT（全店暂停）

```
风控官 G3 发现红线 → 发 HALT（写明是哪个指标、数值多少、红线是多少）
   → 运营总监设置 halt_flag = true
   → 不能再进入这些状态：提交上架、开广告、放量、FBA 发货、补货
   → 已经在跑的广告不会自动关，由老板决定（避免一刀切把正常的品也停了）
   → 复盘、只读分析照常进行
老板处理完后，写 halt_override → 解除
如果只是 FBA 专项指标触发：只挡 FBA 相关的状态，FBM 链路照常
```

## 八、上传通道：现在由老板在后台操作，以后接 API，状态不用变

目前 OpenBot「你的应用」里接的是 sif、sorftime、xydc、1688_scraper 和三个知识库，**还没有 SP-API 和 Ads API 的 MCP**。所以店铺写操作暂时都由老板在后台完成：

| 动作 | 现在（`manual_sc` / `bulk_file`） | 接上 API 后（`sp_api` / `ads_api`） |
|---|---|---|
| 新建 Listing | APPROVED_2 → **AWAIT_UPLOAD**（文案算法师出上架资料包，老板在后台创建，回传 ASIN）→ SUBMITTED | APPROVED_2 → SUBMITTED |
| 开新品广告 | APPROVED_3 → **ADS_AWAIT_UPLOAD**（广告优化师出 Bulk 表格，老板在广告后台上传，回传处理报告）→ ADS_LIVE | APPROVED_3 → ADS_LIVE |
| 改老品文案 | 文案算法师出新旧对比，老板确认后在后台改 | PATCH 接口，一次一个 SKU，先 dry-run |

- `amazon-bulk-upload` 按技能说明是**广告** Bulk 表格工具，不能用来上架商品；商品上架表格（Flat File）的技能还没有
- **规矩：没有回执或处理报告，就不能写 SUBMITTED 或 ADS_LIVE**
- 以后接上 API，只要把 `upload_channel` 改成 `sp_api`，状态机其他部分不用动

## 十、在各个平台怎么落地

| | StarSky（DSH） | OpenBot |
|---|---|---|
| 角色 | 「团队」里的成员（运营总监、选品侦察员……） | 「助手」（运营总监、选品侦察员……） |
| 派活和回复 | 运营总监在群聊「亚马逊运营团队」里 @ 成员，或者在成员各自的对话里派活 | 运营总监给各助手发消息 |
| 审批 | 老板在运营总监的对话（或团队群聊）里亲自回复 | 老板在运营总监对话里亲自回复 |
| 播报 | 运营总监对话；「看板」可以用来看各状态的 SKU | 运营总监对话 |
| 台账存哪里 | 共享 CSV（以后可以接到看板） | 共享 CSV |

> 无论在哪个平台，**台账都要放在对话之外**。对话记录会被压缩、会丢，台账不能丢。
> 其他成员转发的「批准」一律无效，只认老板本人发的消息。

## 十一、完整示例：一个 SKU 从候选到广告

```
M01 TASK     admin→guard        SKU-001 CANDIDATE        "做 G1 风控"
M02 RESULT   guard→admin        CANDIDATE→G1_PASS        g1_verdict=PASS
M03 TASK     admin→warehouse    G1_PASS                  "找 1688 货源，给包装后的尺寸重量"
M04 RESULT   warehouse→admin    G1_PASS→SOURCED          unit_cost_cny=18.5 …
M05 TASK     admin→guard        SOURCED                  "G1b：用 1688 实物图做 IP 复核"
M06 RESULT   guard→admin        SOURCED→IP_CLEARED       g1b_verdict=PASS
M06b TASK    admin→finance      IP_CLEARED               "FBM 和 FBA 各算一遍"
M06c RESULT  finance→admin      IP_CLEARED→AWAIT_GATE1   FBM_TEST，净利率 35%，日预算上限 $15
M07 GATE_REQUEST admin→老板     闸门1 审批卡
M08 GATE_DECISION 老板→admin    "批准 1"                 → APPROVED_1 → CONTENT_WIP
M09 TASK     admin→listing      CONTENT_WIP              写文案
M10 TASK     admin→designer     CONTENT_WIP              设计 7 图套图方案 + 出图 Prompt（和文案同时进行）
M10b RESULT  designer→admin     design_status=done       方案 08_主副图设计方案.md
M10c TASK    admin→imageworker  CONTENT_WIP              按方案出图 + 三项复检
M11 RESULT   listing→admin      copy_status=done
M12 RESULT   imageworker→admin  image_status=done，规范复检全部通过，AI 人物已打标 2 张，读回通过
M13 … QA_CHECK → G2_CHECK → PREVIEW → AWAIT_GATE2 → 老板批准 → APPROVED_2
M14 RESULT   listing→admin      APPROVED_2→AWAIT_UPLOAD  已生成上架表格
M15 老板上传 → 回传处理报告 → SUBMITTED → BUYABLE（ASIN B0XXXX）
M16 … AWAIT_GATE3 → 老板「批准，日预算 12」→ APPROVED_3 → ADS_AWAIT_UPLOAD → 老板上传 → ADS_LIVE
M17 TASK     admin→reviewer     ADS_LIVE→REVIEWING       next_review_at = 上架后第 3 天
```
