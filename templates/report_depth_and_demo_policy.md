# 沙龙报告深度与演示直跑统一政策

版本：1.1（2026-07-22）

本政策适用于沙龙工具包中的总控 Skill、业务 Skill、Markdown 报告与 HTML 报告。目标是保留新版工作流的状态机、产物契约和事实边界，同时恢复 7·18 沙龙输出的分析深度、教学价值和可执行性。

## 0. 两条互相独立的模式轴（先分清，别混用）

本政策里有两组模式，它们**不是一回事，可以自由组合**：

| 轴 | 取值 | 管什么 | 触发 |
|---|---|---|---|
| **事实边界轴** | `production` / `demo_direct_run` | 能不能编、能不能上传、要不要重复确认 | 用户说「测试走流程 / 直接用」→ demo |
| **广度轴** | `full_delivery` / `salon_live` | 取多少数、写多少行 | 用户显式写「运行模式：salon_live」才降档 |

例：真实店铺优化 = `production` + `full_delivery`；课堂演示 = `demo_direct_run` + `salon_live`。
不得把「demo」当成缩短报告的理由（那是广度轴的事），也不得把「salon_live」当成可以编数据的理由（那是事实轴的事）。

## 1. 两种运行模式

### production

用于真实上架、真实广告上传、对外发布或会造成外部状态变化的任务。保留事实确认、IP 决策、真实 SKU/ASIN、上传前审核和不可逆操作确认。

### demo_direct_run

用于课堂演示、内部测试、流程验收和用户明确说“直接用 / 测试走流程 / 不要重复问授权”的任务。

- 已有输入足以继续时直接执行，不重复询问授权或确认。
- 缺少非关键数据时使用 `demo_default`、`AI推断`、`待确认`、`条件性结论`。
- 缺真实 SKU/ASIN 时可以生成 `DEMO_ONLY_NOT_UPLOADABLE` 产物，但不得声称可上传。
- 供应商资料选择 `deferred` 后继续，不把缺字段升级为流程阻断。
- 用户明确要求生成图片、HTML、广告架构或演示 Bulk 时，该请求本身即视为本步骤执行指令，不再二次询问。
- 不要求用户证明其对供应商图片、资料或案例拥有授权；仅在产物中标注素材来源和“上线前自行确认使用权”。

## 2. 闸门分类

### hard_block

只有以下情况允许停止主线：

1. 登录、验证码、滑块或必须由用户完成的交互。
2. IP 决策：`fix_required / accept_risk / abort`。
3. 用户要求“可直接上传”的 Bulk，但缺真实 SKU/ASIN、官方模板或必要生产字段。
4. 不可逆操作、对外发布、真实上传、付费或外部系统状态变更。
5. 继续执行会伪造事实、冒充真实 MCP 数据或违反明确合规红线。

### soft_warning

下列情况写入报告但继续：

- 非关键供应商字段缺失或暂不回填。
- 素材授权未核实但仅用于内部演示。
- MCP 某个补充字段缺失，但已有导出表或其他证据可完成分析。
- 预算、CPC、CVR、FBA 费等可用区间或公式表达。
- 演示图片、广告参数或变体尚未生产确认。

## 3. 7·18 深度保留契约

“简洁”只允许删除重复表达，不允许删除判断机制。报告至少保留：

1. 结论及其证据链，不只给结论。
2. 数据来源、时间、字段缺口与事实/推断边界。
3. 计算公式、变量、示例代入和敏感性区间。
4. 竞品/关键词/供应商/广告对象的明细表，不用几条摘要代替全量对象。
5. 资深运营判断：为什么这样做、看到什么信号要改、失败条件是什么。
6. 可直接执行的清单、命名、字段映射、否词、埋词、投放或询盘动作。
7. 运行节奏：首日、3 天、7 天、14 天或适合该业务的复盘周期。
8. 正例、反例和常见坑，保证课堂可解释、团队可复用。
9. 下游结构化产物及字段契约。
10. `acceptance_checks`，缺少 P0 模块时报告必须判定为不合格并补写。

禁止把阶段报告写成纯目录或文件索引。阶段报告必须给出跨报告综合判断、冲突、关键数字、决策条件与下一阶段动作。


## 3.0 ⛔ 两种运行模式：full_delivery / salon_live（v2026-07-28 新增）

### 为什么加这一节

2026-07-28 宠物用品实测耗时：

| 步骤 | 耗时 |
|---|---:|
| S1 全链（L1–L3 + 市场穿透 + 竞品池 + 供应链 + IP） | 20m48s |
| 补 SKU + 计费重重算 + IP 补图 | **47m07s** |
| SIF 词库清洗 + 场景库 + HTML | **28m22s** |

3.5 小时现场扣掉开场只剩 180 分钟要跑 5 个板块 —— **数学上不成立**。

§3.1 的深度下限当初是为了防「有数据不写」，方向没错。
但现场的问题相反：**取数太多、写太厚**。同一套下限套两种场合，必然有一边崩。

### 硬规则：降广度，不降深度

| | `full_delivery`（默认） | `salon_live`（现场演示） |
|---|---|---|
| **章节结构** | 全部 | **全部，一节不少** |
| **判据与硬规则** | 全部 | **全部，一条不减** |
| 最强反方 / Gate / 允许成本倒算 | 必出 | **必出** |
| 数据解释窗口 / 覆盖率降级 | 必出 | **必出** |
| — | — | — |
| 阶段综合报告行数 | ≥300 | **≥90** |
| 市场穿透行数 | ≥250 | **≥80** |
| 关键词库报告行数 | ≥200 | **≥70** |
| Listing 文案报告行数 | ≥200 | **≥70** |
| 广告架构报告行数 | ≥250 | **≥80** |
| 表格数据行 | 见 §3.1 | **各降至 1/3** |

> **判定口径**：`salon_live` 下**结构完整性仍按 §3.1 的标题数要求**，
> 只放宽行数与表格行数。**少一个章节判不合格，行数少不算。**

### MCP 取数下限的演示档

§3.3 的九项在 `salon_live` 下改为：

| # | 项 | full_delivery | salon_live |
|---:|---|---|---|
| 1 | 类目节点横向对比 | ≥3 个 | **1 个**（写明只取 1 个及其影响） |
| 2 | 竞品明细 | ≥15 个 ASIN | **≥5 个** |
| 3 | 变体穿透 | Top10 逐个 | **Top3** |
| 4 | 上架日期分层 | 全量 | **仅头部 5 个** |
| 5 | 双时间窗 | 近30天 + 旺季月 | **近30天**（旺季月标 not_run） |
| 6 | 类目月度趋势 | 24 个月 | **12 个月** |
| 7 | 评论样本 | ≥100 条 | **≥30 条** |
| 8 | 关键词侧信号 | ≥1 次 | ≥1 次（不变） |
| 9 | 最晚下单日反推 | 必须 | **必须**（不吃数据量） |

关键词清洗在 `salon_live` 下：**只处理搜索量 Top 60 的相关词**，其余进「未处理词表」并写明条数。


### HTML 只在阶段末出一次（salon_live 强制）

**实测问题**：2026-07-28 S1 一轮生成了 **5 份 HTML**（SKU锁定 / L2成本 / 市场穿透 / IP初筛 / S1综合）。
每份都要现场重写一套 HTML 皮、判数据形态、生成图表 ——
**光 HTML 可能吃掉 15–25 分钟**。而中间那 4 份**没人会看**，读者只看阶段末那一份。

**规则**：

| 模式 | HTML 产出 |
|---|---|
| `full_delivery` | 按各 Skill 既有约定 |
| **`salon_live`** | **每个阶段只出 1 份 HTML —— 阶段综合报告**<br>中间步骤（选品筛选、成本、竞品池、IP…）**一律只出 Markdown** |

| 阶段 | salon_live 唯一 HTML |
|---|---|
| S1 | `阶段_S1_选品可行性研究报告.html` |
| S2 | `阶段_S2_词库与文案.html`（或既有命名） |
| S3 | `阶段_S3_视觉.html` |
| S4 | `阶段_S4_广告.html` |

**例外**：用户在口令里显式点名「某某报告也要 HTML」时才补出。

> **为什么中间步骤不需要 HTML**：Markdown 在编辑器里直接可读，
> HTML 的价值是「能发给别人看」—— 中间产物不会发给别人。

---

### ⛔ 三条不许降的

1. **章节不许少** —— 少一节就看不出这套东西的完整形态，演示就失去意义
2. **判据不许软** —— 最强反方、Pass/Hold/Stop、允许成本倒算、覆盖率降级，一条都不能省
3. **不许把 `salon_live` 的结论当真实结论** —— 报告顶部必须标：

```markdown
> ⚠️ 本报告为 **salon_live 演示模式**：样本量按演示档降低
> （竞品 5 个 / 评论 30 条 / 类目节点 1 个 / 词 Top60）。
> 结构与判据与完整模式一致，但**数据广度不足以支撑真实上线决策**。
> 完整模式重跑口令见文末。
```

### 怎么触发

用户在口令里写 `运行模式：salon_live` 即可。
未指定时**默认 full_delivery** —— 演示模式必须显式声明，不得自动降级。

### 与既有那条禁令的关系

§3.1 下方原有一句：

> 未达标时不得以"演示模式""用户要求简洁""数据不足"为由通过。

**这句仍然有效，但适用于 `full_delivery`。**
它防的是「该写的不写」；`salon_live` 是**显式声明的、有独立下限的另一套标准**，
不是拿"演示"当借口偷工。两者不冲突。

### 3.0.5 决策首屏（强制，v2026-08-25 新增）

行数下限（§3.1）只能防「写薄」，防不住「写厚而空」——实测已两次出现：市场报告「章节多≠结论硬」、文案报告「351 行结构完整但文案不行」。因此每份阶段报告与单点任务报告，**正文第一节必须是「决策首屏」**，≤30 行，包含且仅包含：

| 行 | 必须写 |
|---|---|
| 结论一句 | 做/不做、改/不改、Pass/Hold/Stop——一句话，不带"视情况而定" |
| 关键数字 3–5 个 | 每个带来源与时间窗（如「盈亏 ACOS 31%，来自 单位经济.yaml 2026-08-24」）；缺数写 null+原因，不许空着 |
| 下一步动作 | 谁、做什么、在哪里做（后台路径/文件路径） |
| 失败条件 | 看到什么信号说明这个结论错了、该回滚或换路 |
| 数据可信度 | 一行：本报告基于什么数据档位（full/降级/演示），哪个结论因此不能当真 |

判定规则：
- **缺决策首屏 = P0 不合格**，与缺章节同级。
- 决策首屏里的结论必须与正文判据一致；首屏说 Pass、正文最强反方未被回应的，判不合格。
- 首屏之后的正文仍按 §3 十条与 §3.1 下限执行；首屏不是摘要替代品，是决策入口。

> 读者判断标准：老板只读首屏 30 行就能拍板或知道找谁拍板；读不出来就是不合格，行数再多也不合格。

### 3.1 量化深度下限（强制自检）

**R01 M2 对 S1 的替代规则**：S1 市场报告与综合报告不再按下表的行数、表行数、标题数下限通过或拒绝；改按 `s1_report_module_contract.yaml` 的必备字段逐项核对。缺数据须明确字段、原因与影响，不能凑字数。任意两段≥200字完全相同判失败；首屏与正文唯一结论必须一致；综合报告保留完整深度，不设行数上限；继续检查章节、重复、数值与结论。取数下限、来源真实性、Hash、成本/IP与授权门禁保持，下表对其他阶段的原规则不变。历史S1行数只作为审计备注，不作为验收依据。

上面 10 条是定性要求，实测中会被"写全了但每条只有一句话"绕过。因此追加可机检的下限：

| 报告 | 最少行数 | 最少表格数据行 | 最少二级以上标题 |
|---|---:|---:|---:|
| 阶段综合报告（S1/S2/S3/S4/S5 的 `阶段_*.md`） | **300** | **120** | **25** |
| 市场穿透报告 | 250 | 100 | 20 |
| 关键词库报告 | 200 | 全量词表另计 | 15 |
| Listing 文案报告 | 200 | 50 | 20 |
| 广告架构报告 | 250 | 90 | 20 |
| 单点任务报告 | 120 | 30 | 10 |

自检命令（生成后必须跑，不达标即判 P0 不合格并补写）：

```bash
f=S1_选品板块/_阶段总览/阶段_S1_选品可行性研究报告.md
echo "行 $(wc -l <$f) | 表行 $(grep -c '^|' $f) | 标题 $(grep -c '^#' $f)"
```

**未达标时不得以"演示模式""用户要求简洁""数据不足"为由通过。** 数据不足时正确做法是把缺口、影响范围、补数路径和失败阈值写足，而不是缩短报告 —— 缺口分析本身就是 P0 内容。

### 3.2 加载资料包时深度只增不减（强制）

当本轮加载了企业资料包（`profile_mode` 非 `base`）时：

- 阶段报告的行数、表格行数**不得低于同类目/同阶段的通用模式基线**
- 每个被注入的来源类别（keyword / advertising / supplier / logistics / visual_reference / sop / compliance）至少在报告中体现一次，或写明"本阶段不适用"及原因
- 资料包提供的口径（费率、线路、阈值、方法名）必须**原样带进报告**，不得只用其推导结果

> **反模式**：加载了 100+ 份资料，报告反而比不加载时更短。这说明资料被当成了"读过即可"，而不是"必须消费"。出现此情况判定为注入失败，不是"精简得当"。

### 3.3 MCP 取数下限（强制）

§3.1 的深度下限只能防止"有数据不写"，防不住"根本没取数"。实测出现过：只调 1 次 `category_report`、只取 6 个竞品、0 个类目节点对比，然后把这点数据写得"符合深度要求"——底座数据量只有正常轮次的三分之一。

因此对每个阶段规定**最少调用清单**，不达标不得出报告。

#### 市场穿透（`amazon-market-research`）

| # | 项 | 下限 | 工具 |
|---|---|---|---|
| 1 | 类目节点横向对比 | **≥3 个**相关节点各拉一次 | `category_report` |
| 2 | 竞品明细 | **≥15 个 ASIN** 完整字段（销量/价格/评分/评论/上架日期/FBA/毛利） | `category_report` + `product_detail` |
| 3 | **变体穿透** | Top10 逐个展开变体 | `product_variations` |
| 4 | **上架日期分层** | 区分「近两年新链接」与老链接 | `product_detail.online_date` |
| 5 | **双时间窗** | 近 30 天 Top100 **+ 旺季月 Top100** | `category_report` + `category_report_from_history` |
| 6 | **类目月度趋势** | 以 1 月为 100% 的各月指数 | `category_trend` |
| 7 | 评论样本 | **≥100 条** | `product_reviews` / `product_customers_say` |
| 8 | 关键词侧信号 | ≥1 次 | `keyword_list` / `keyword_trend` |
| **9** | **最晚下单日反推** | **必须给出具体日期与来得及/来不及的判定** | 无需 MCP，由 6 + 补货提前期推导 |

**第 3、4、5、6 条是 2026-07-26 据外部内测反馈新增，理由必须写进报告：**

- **变体穿透（3）**：Top100 是**链接维度**，每条链接只呈现其中一个变体。对尺寸/颜色/数量/套装分化大的类目，**市场均价必然失真**（套装件数多的售价天然高）。必须给出「按单件折算」后的真实价格带，并说明热销的是哪些尺寸/颜色/套装形式。
- **上架日期分层（4）**：老链接的成功不可复制。**能不能切进去，看的是近两年新链接**——它们的形态、变体形式、套装组合为什么能成功，才是可迁移的证据。注意取的是**链接维度的最早上架日期**。
- **双时间窗（5）**：季节品只看近 30 天没有意义（圣诞品 3 月看等于没看）。旺季月 Top100 与近 30 天 Top100 的**榜单构成差异**本身就是结论。
- **月度趋势（6）**：给出以某月为 100% 的各月指数与完整曲线。节日性产品还需看周维度峰值与起量—跌落曲线。

#### 第 9 项「最晚下单日」为独立强制项（不是月度趋势的附注）

**实测教训**：把它写成第 6 项的说明文字时，模型做出了 24 个月完整曲线，却**没有反推下单日** —— 数据做到位了，决策没走出来。因此单列为可检项。

月度趋势只是**数据**，下单日才是**决策**。两者之间隔着一次乘法，必须显式做完：

```text
旺季峰值月（来自第 6 项）
    减去  补货总提前期（来自企业基线 T-09，如 58-86 天普船档）
    ────────────────────────────────
    = 最晚下单日区间
    对比今天 → 来得及 / 来不及 / 需换快船
```

**报告必须输出的四行**（缺任一即第 9 项不达标）：

| 必须写 | 示例 |
|---|---|
| 旺季峰值月及其指数 | 8 月为全年峰值，指数 117–121 |
| 采用的提前期与来源 | 58–86 天（T-09 普船档，四家货代实测） |
| **最晚下单日区间** | **5 月 7 日 ~ 6 月 4 日** |
| **对比今天的判定** | 今天 7/26，**2026 旺季已错过**；本轮定位为 2027 旺季前验证期，或改快船（提前期压至 ~68 天）重算 |

**判定必须给结论，不能只列日期。** 「来不及」是一个会改变选品决策的结论 —— 它决定这个品现在是"抓紧上"还是"当作明年验证"，不能让读者自己去算。

若企业基线尚无 T-09（提前期未确认），则写明"提前期未确认，无法反推下单日"并列出确认后需重算的项，**不得跳过本项**。

| 项 | 下限 |
|---|---|
| 导出表 | 有网页导出时以其为证据底座；无则标 `MCP-仅拉取` |
| 竞品 ASIN | 与 `competitor_asin_pool.yaml` 一致，不得私自缩减 |
| MCP 验词 | ≥1 次，或写明"MCP 已跳过"及原因 |

#### 通用强制

1. **每个阶段至少一份 `*_data_source_log.yaml`**，逐次记录工具名、参数、调用时间、返回条数。**无日志即判不合格。**
2. **预置输入不豁免探查**：用户或上游已提供竞品池 / ASIN 清单 / 类目节点时，**仍须完成类目节点对比、变体穿透、趋势查询**——预置只免去"找竞品"这一步，不免去市场探查。
   > 这是实测踩过的坑：竞品池被预先递到手上后，AI 直接使用，跳过了整个市场探查过程，取数量降到三分之一。
3. 任一下限未达标时，报告须在数据解释窗口写明**缺哪项、为何缺、影响哪些结论**，且阶段状态不得写为完成。

### 3.4 汇率必须来自当日快照（强制）

**实测问题**：S1 财务公式里写死 `(采购价+头程)/7.20`，标注为"模拟汇率"。而同期真实快照是 **6.68**（含 1.5% 缓冲后的 effective_purchase_rate）—— **差 7.8%**，直接把落地成本、广告前贡献和盈亏 ACOS 全部算偏。

更严重的是：7-25 那轮已经生成过 `fx_rate_snapshot.yaml` 与刷新脚本，但它们**只留在那个 run 目录里**，没有沉淀成共享工具，所以新 run 又退回了硬编码。

#### 强制行为

1. **任何涉及 CNY↔USD 换算的步骤，执行前必须先确保当前 run 存在 `fx_rate_snapshot.yaml`**。不存在则先跑：

   ```text
   <python> <插件目录>/scripts/refresh_fx_snapshot.py --run "<产品根>"
   ```

   脚本只在快照缺失或超过 24 小时时才联网取数，仍在有效期内直接复用。退出码：`0` 快照可用；`2` 刷新失败、沿用了旧快照（已写入 `refresh_failures` 并提示过期小时数，报告必须如实标注）；`1` 没有任何可用快照（不会写文件，也不会编造汇率）。联网取不到时，由**用户亲自**给出参考汇率：加 `--rate <1美元兑人民币>`，来源会标注为“用户手填”。收到银行/支付实际结汇价后用 `--settlement-rate` 记录，成本测算会优先使用它。

2. **禁止在公式、表格或正文中写死汇率数字**。所有换算必须引用快照字段：

   | 用途 | 取哪个字段 |
   |---|---|
   | 成本测算、利润推导（默认） | `fx_buffer.effective_purchase_rate`（含缓冲，保守） |
   | 单纯汇率展示、对外说明 | `reference_rate` |
   | 已收到银行/支付实际结汇价 | `settlement_override.actual_settlement_rate`（优先级最高） |

3. **每处换算必须带口径标注**，格式：

   ```text
   ¥5.542 ÷ 6.680174（USD/CNY effective_purchase_rate，快照 2026-07-26，含 1.5% 缓冲）= $0.830
   ```

   只写 `/6.68` 而不说明来源与口径，等同于硬编码。

4. **快照过期必须刷新**：`retrieved_at_utc` 距当前超过 **24 小时**即视为过期，须重新执行刷新脚本；刷新失败时如实记录 `refresh_failures` 并标注"使用 N 小时前快照"，不得静默沿用。

5. **物流比价不换汇**（见 `data_intake_read_contract.md` §2.2 相关约定）：货代报价、供应商报价一律保留人民币原币，只在交接财务模型时换算一次。

> **判定**：报告中出现未绑定快照的汇率数字（如"模拟汇率 7.20"）即判财务章节不合格。
> 缺快照时正确做法是**先刷新再算**，而不是"先用个约整数演示"——汇率不是可以拍脑袋的演示参数，它是乘在每一件货成本上的系数。

## 4. 报告验收层级

- P0：结论、证据、全量关键明细、计算/推导、风险、执行动作、下游数据包。缺一即不合格。
- P1：分层统计、交叉洞察、案例、替代方案、复盘节奏。缺失必须解释。
- P2：延伸阅读、装饰性图表、非关键背景。可按篇幅取舍。

任何“优化”“精简”“重构”都必须先与参考标准答案逐章节对照；如果参考输出中存在有效机制，不得仅因篇幅删除。

## 7. 数据解释窗口（每个阶段强制）

缺数据不是默认停止条件。每个业务 Skill 完成后，报告正文和 handoff 必须出现一次“数据解释窗口”，用固定五栏解释当前输入质量：

| 栏位 | 必须回答 |
|---|---|
| 已获取事实 | 本步从 MCP、页面、文件、图片/OCR、用户资料中实际取得了什么 |
| 自动提取/推导 | 哪些信息由已有证据计算、翻译、归一化或合理推导，证据在哪里 |
| 模拟参数 | 为继续流程采用了哪些区间、demo_default 或条件性假设 |
| 缺失及影响 | 缺什么；只影响精度、限制前台承诺，还是构成真正 hard_block |
| 继续与修订 | 当前如何继续；用户以后补数时从哪个节点重算、影响哪些产物 |

解释窗口是说明和选择入口，不是额外审批。默认策略为 `explain_and_continue`：

- 能从现有资料摘取的先摘取，不要求用户重复提供。
- 能用区间或条件性结论继续的，继续生成完整报告，不得降级为简版。
- 数据不足只限制该字段的使用范围，例如“不可写进 Amazon 前台”，不限制不依赖该字段的市场、词库、视觉框架或广告结构分析。
- 用户后补数据时执行 `impact_scoped_revision`，只重算受影响产物，保留旧版与修订记录。

建议在 `workflow_state.yaml` 写入：

```yaml
data_policy:
  missing_data_behavior: explain_and_continue
  auto_extract_existing_sources: true
  conditional_simulation: true
  late_data_revision: impact_scoped
data_explanation_windows: []
revision_queue: []
```

## 8. 1688 上架事实自动提取政策

1688 抓取结束后，不能只交付原始页面报告并等待供应商。必须立即从结构化 JSON、标题、SKU、价格阶梯、件重尺、产品属性、详情 HTML、下载图片/OCR、视频信息和可见评价中提取所有可用的 Amazon 上架字段，输出：

- `S1_选品板块/1688-product-detail-scraper/03_extracted_listing_facts.yaml`
- `S1_选品板块/1688-product-detail-scraper/03C_上架数据解释与续跑说明.md`

每个字段必须含：`value`、`source_status`、`evidence`、`confidence`、`allowed_use`、`revision_trigger`。

`source_status`：`page_confirmed / media_derived / ai_inferred / missing`。  
`allowed_use`：`listing_ready / conditional_draft / internal_simulation_only / blocked_claim`。

用户没有回填时，自动把可用字段合并进 `03_product_facts.yaml`，状态写为 `deferred_auto_extracted`，再用区间完成 03B 复算并进入后续步骤。不得因为材质、包装或尺寸中的部分字段缺失，把完整报告压成简版。

后补数据的影响映射：

- 尺寸/重量/采购价/头程 → 03B、S1 财务、盈亏 ACOS、广告竞价。
- 材质/配件/适配范围/性能 → IP、Listing、主副图、A+、视频中的相关声明。
- 包装套数/变体 → Listing、视觉、库存计划和广告 SKU 路由。
- 合规/专利证据 → IP 决策、blacklist 及所有消费者可见声明。
- 媒体原图 → 垫图 manifest、主副图、A+、视频，不要求重跑无关市场和词库步骤。

## 10. 阶段顺序

沙龙主线固定：

```text
IP 侵权报告
→ 综合可行性报告（S1 选品阶段最终报告）
```

## 11. 大体积录屏与视觉案例读取

- 现场长录屏、大体积分享视频默认只登记文件名、大小、时长，不完整转写或逐帧分析。
- 优先读取配套 PPT、讲义、Prompt、分镜、成稿和图片案例。
- 对视觉/视频能力成熟的嘉宾或案例，可选择代表样本，抽取首帧、关键帧、尾帧或指定 5–10 秒片段，用于学习构图、动作、镜头和失败控制。
- 节省 Token 不能成为完全跳过视觉方法的理由；也不能为了“深度”无差别读取数小时录屏。

## 12. 外置企业资料包与任意类目

用户可在启动时一次性给出：

```text
资料包根目录（可选）：
输入你的类目名称：
```

资料包不是类目白名单，也不需要为每个类目复制一套 Skill。总控以「强母版工作流 + 共享企业资料 + 用户任意类目资料夹 + 当前产品事实/MCP 数据」形成当前 run 的临时运行叠层。

- 仅索引用户明确指定的根目录；已有资料夹无需迁移。
- 根目录默认只读。所有 manifest、索引、冲突清单与运行时 overlay 写在当前产品 run，不写回源资料夹。
- 先轻量读取路径、文件类型、Excel/CSV 表头和基础媒体元数据；大视频仅登记元数据，除非用户指定才抽样读取。
- 类目名称允许自由文本与层级路径。必须拒绝 `..`、绝对路径和任何根目录外解析结果；若用户只给根目录，先在 `condition_select` 收敛方向后再解析资料夹。
- 已给根目录且根目录可写、目标资料夹不存在时，允许按资料包模板创建简洁骨架；无法创建时继续通用模式，不把它当阻断。
- 当前产品事实、页面抓取和本轮 MCP 数据优先于企业历史资料；企业资料只作为历史证据、起始策略、品牌边界和表达参考。平台合规、IP 与用户明确禁区不允许被历史资料放宽。
- 每个阶段仅显示一次简短注入行，并在数据解释窗口保留来源与使用边界；不得重复要求用户选择“V2”或重复授权。

阶段注入范围：S1 用产品案例/供应链/合规/预算；S2 用词库/Listing/否词/品牌语气；S3 用视觉参考；S4 用广告报表/命名/预算/店铺基线；S5 与 Ops 只把历史资料作为镜头或诊断参考。

## 13. 沙龙实演成熟度与阶段验收

工作流实演成熟度不是产品的市场成功概率。使用 `templates/salon_stage_acceptance.schema.yaml` 在 state 中维护 S1、S2、S3、S4、S5、Ops 的状态、证据模式和验收时间。

- S1：选品→市场→供应链→IP→综合可行性报告（含 Tabler HTML）后才可进入 S2。
- S2：竞品确认→词库→Listing，词库与 Listing 是完整交付而非摘要。
- S3：本品垫图→主副图→Premium A+；Premium A+ 每模块必须同时有 Desktop 与 Mobile 两套。
- S4：课堂同日只验收广告计划、架构与演示/生产 Bulk；真实上传、跑数、报表下载、优化和修订 Bulk 是上线后的延迟闭环。
- 视频（属 S3 视觉板块）：分镜与生产包在 S3 完成；成片验收可排在 Bulk 后，`package_ready` 与 `final_accepted` 分态。
- Ops：上线后以真实店铺/广告/库存数据或首次快照开始巡检，不反向阻断新品主链。

任何阶段只有产物、证据边界、数据解释窗口和 acceptance checks 同时满足时，才能记为 `accepted_for_demo` 或 `accepted_with_real_data`。
