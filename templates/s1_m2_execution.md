# R01 M2 新案九步执行（旧案原进度）

适用 `s1_execution.roadmap_version: r01.m2`。已有未标版本的案子按 `legacy.m1` 和封存的原九步继续，编号、标题、MCP/KB和业务门禁一起保留；禁止套新标题、自动迁移或重跑旧选品。新案 init 封存完整 `roadmap_steps`。路线图只从 `s1_roadmap.resolve_roadmap(home, root)` 读取，不凭记忆重写。

## 从真实产品根开始

已有 workflow_state.yaml 的目录就是产品根。新案使用本宿主安装根 `<home>` 和安装记录 Python，执行 `scripts/s1_intake.py --create-product --host codex|claude --workspace "当前用户工作区"`；宿主参数按实际环境选一个，禁止把 Claude 根写到 Codex。已处于 product_runs 时不再套第二层；用户「换目录 路径」按其明确目录处理。第1卡显示实际产品文件夹链接。选定名称后只用 rename_product_root.py 改名，旧路径保留目录软链接/Windows junction，导航记忆同步；不用临时脚本批量替换历史文件。

用 `s1_intake.py --root "产品根" --reply "用户真实一行回复"` 写条件。默认 E = US、$15–25、广告前40%；目标毛利可选30/40/50%，首批预算可空。保留原话和各字段 default_assumption/user_attested；系统默认不是业务证据，也不是采购授权。

## 文件放哪（每步都适用）

- 每步开始：`begin` 的输出就是本步工作包（要调的数据源、知识库及参数、本步做法、停下条件、收尾命令），照它做，不另翻本文件和其他说明；中途要再看用 `workflow_flow.py "产品根" pack --stage S1`。
- MCP 原始回包：本步调用完后运行一次 `scripts/capture_mcp.py --root "产品根" --step N`，从本对话原生记录自动存进 `S1_选品板块/amazon-market-research/运行数据/`，并生成知识库登记草稿；不要手抄回包。**Codex code mode**（MCP 在 `exec` 脚本里调用）：回包是你的脚本自己打印的，只有“原样打印调用结果”的写法才会入档——`const r = await tools.mcp__<服务>__<工具>({参数写死}); text(JSON.stringify(r));`；并行用 `const r = await Promise.allSettled([tools.…(…), tools.…(…)]); for (const x of r) text(JSON.stringify(x));`。不要只打印摘要或拼字段（如 `{kb: r.structuredContent.kb}`），不要用 map / 循环 / 变量传参；这类调用 capture_mcp 会报“回包无法核验”（不是调用失败），要重调一次。capture_mcp 的 `problems` 里每一类原因都单独写明（没调用 / 回包无法核验 / 调用报错 / 记录读不了 / 存盘失败 / 知识库是旧版），照它说的办，不要自己判断“可能失败了”。读不到对话记录时才用 `scripts/save_mcp_response.py --root "产品根" --tool <数据源>__<工具> --args '<参数JSON>' --response-file <回包或->` 逐个存。
- 业务文件放对应技能目录 `S1_选品板块/<技能>/`。
- 知识库：照工作包列出的顺序和参数调用；`capture_mcp.py` 生成的草稿已填好回包，只填每项 card_ids 和 usage（从 returned_cards 里挑），再 `scripts/save_kb_evidence.py --root "产品根" --step N --calls <草稿>` 一次登记（失败写 error 并加 --reason）。之后本步生成器会自动把“知识库依据”写进报告。
- `00_总控/…/运行数据/流程控制/`、`receipts/`、`紧凑业务报告/` 只放插件自己的流程记录，写进去会被拒绝。
- 自己写的步骤报告（selection_md / demand_md / market_md / promotion_md / ip_md 等），record 前运行 `scripts/kb_report_contract.py --root "产品根" --step N --role <角色> --file <报告相对路径>`，把本步已登记的「知识库依据」小节和卡号引用写进去，并按验收规则统一数字显示精度；不要自己手写这一节，否则验收会报"缺知识库依据小节 / 缺引用"。
- 步骤卡：`cards` 输出的卡原样复制为本轮 final 正文第一块，一个字都不改、不缩写、不重写结论。插件按原文逐字核对，改过的卡核对不通过，下一轮会被要求重发，每步白多一张卡。
- 每步收尾：`scripts/workflow_flow.py "产品根" draft --stage S1 --receipt <临时文件.json>` 生成回执草稿，本步的知识库登记、已存的 MCP 回包、Skill 名和必需产物名都已填好；只补 summary、decision、值为 null 的产物路径和 tools_run，再 `record --stage S1 --receipt` 同一文件。不要读 workflow_flow / s1_flow / workflow_checks / host_support 源码猜回执格式；record 或 ack 报错就按报错文字补，不去翻实现。

## 按九步执行

1. **条件确认**：站点、价格带、模式、目标毛利和可选首批预算；不重开长访谈。用原生命令 `scripts/s1_intake.py --root "产品根" --reply "<用户原话>"` 写 intake_yaml（`00A_quick_select.yaml`）和 intake_md（`00_总控/starsky-fullchain-workflow/00A_选品需求确认单.md`），不要自己拼这两个文件。
2. **方向筛选**：3–5个方向，competition / differentiation / margin_barrier / market_capacity / trend 五轴各1–5分。每轴 `{score,evidence:{value,source,time_window},missing_reason}`；数字依据缺失时score=null并写具体原因，不给印象分。用户选1个方向；真实回复写入 user_reply，decision.message逐字相同且selection为具体编号。 原生做法（R06.1）：①方向表写成 `S1_选品板块/jingpu-product-selection/02_方向初筛.yaml`：`candidates: [{n: 编号, name: 方向名, scores: {competition|differentiation|margin_barrier|market_capacity|trend: {score: 1–5 或 null, evidence: {value: 数字, source: "mcp_calls__<工具>.json 里的键与字段", time_window}, missing_reason}}}]`，3–5 个；②同目录写一页 `02_方向初筛.md`（每个方向一句话结论加五轴表，缺数写缺什么）；③运行 `scripts/s1_selection.py --root "产品根" --input S1_选品板块/jingpu-product-selection/02_方向初筛.yaml` 生成标准 00_product_selection.yaml；④回执 artifacts：selection_md、selection_yaml 指向这两份文件。不用读 r01_native / s1_flow / kb_report_contract 源码找写法。
3. **需求验证门**：对目标形态+人群拉核心词月搜、同形态Top10价格/销量/评论、Top3各12个月趋势、至少100条真实评论。`02_demand_validation.yaml` 保存 validated_positioning `{form,audience,core_keywords,target_size,category}`，core_keyword、same_form_top10、top3_trends、reviews；数值/文本事实用 `{value,source:{path,selector},time_window}` 绑定原回包。先 `scripts/s1_research_gates.py --root "产品根" --demand-template <临时.yaml>` 拿填写模板（字段和写法都在注释里），写成 `S1_选品板块/amazon-market-research/02_demand_validation.yaml` 后用 `--check-demand <该文件>` 先自查缺项，再 record；不用读 s1_research_gates 源码找格式。0评论/0趋势绝不以一页缺口说明放行。

   **R05 新案必须同时完成相邻类目对比**：`s1_execution.category_comparison_contract: r05.adjacent.v1` 的案子，第3步实际调用 `category_tree({amz_site,node_id:直接父节点})`，核实目标节点与相邻子类来自同一直接父节点；先用当前工具清单和真实类目树确定目标、父节点，不凭记忆或关键词猜 ID。`category_tree` 不传 node_id 时只返回一级和二级类目，需要时沿实际返回的节点逐层查到直接父节点。保留完整类目树响应与每个选择的理由；默认从真实同父节点子类选3个不同相邻类目，排除目标自身。若需业务筛选，plan.selected 显式列3个 `{node_id,reason}`，仍须由真实类目树证明关联。

   在 `02_demand_validation.yaml` 增加 `category_comparison_plan: {amz_site:实际站点,target_node_id:实际目标节点,parent_node_id:真实直接父节点,query_start:YYYY-MM-DD,query_date:YYYY-MM-DD}`；起止日期须在同一自然月、跨度3–40天。然后必须运行下面的正式续拉入口，即使核心词/Top10/趋势/评论已经齐全也要运行。入口实际拉取树与3个 `category_report({amz_site,node_id,query_start,query_date})`，自动生成本目录 `comparison_scope.yaml`（schema=r05.adjacent.v1）和完整原始调用 bundle；请求/回包ID、tool、全部参数、完整响应、数值统计、来源SHA绑定，市场事实和C3再次按原回包校验，不能以自填 observed/页数充数。

   只有完整真实发现回包证明目标在直接父节点下没有任何其他相邻子类时，才允许 evidence-backed `not_applicable`（跳过，不计达标）。工具缺失/失败、空或不完整的类目树、仅1–2个可用相邻类目或报表、ID/站点/时间错配均保留硬缺口，不能标NA，也不能用「接受低需求」豁免。以后真实3类数据齐全后自动清除旧NA。未标此新契约的旧案保留原流程与历史来源，不自动重跑。

   缺数先按 Sorftime 当前工具 schema 构造 collection.requests（tool+arguments），实际调用 product_reviews / product_trend / keyword_search_results / category_report。可用正式续拉入口 `s1_research_gates.py --root "产品根" --continue-demand "S1_选品板块/amazon-market-research/02_demand_validation.yaml"`。原始回包、参数、真实错误码和超时完整并入本步结构化文件；有成功回包必须先读完并规范化到上述字段再复检，不能收到回包却只发缺口卡。MCP成功不代表需求已通过。评论按实际原始回包位置及身份去重，不按自填ID或数量宣称；不同真实评论可以同文。仅真实数量仍不足才给「换方向 / 接受低需求继续」；仅真实用户选择可记decision.action=accept_low_demand、outcome=partial，缺项和真实错误留在报告，不能改成需求通过。来源篡改、格式坏、形态/人群/核心词错配属于硬错误，接受低需求不能解除，也不能跳过真实自动续拉。
4. **选款 + 对标**：目标规格、3个对标ASIN、差评VOC、站外讨论、竞争格局。执行≤5分钟IP快筛：对标品牌商标、产品名+design patent真实检索；source/date/result保留。快筛用原生命令：`skills/amazon-ip-risk-assessment/scripts/compliance_ruler.py --run "产品根" --quick-template <临时.yaml>` 生成填写模板，两项检索后只填模板里的 status/date/result/evidence_urls 或 screenshots/assessment，再 `compliance_ruler.py --run "产品根" --quick-screen <同一文件>` 判定并写 `S1_选品板块/amazon-ip-risk-assessment/04_ip_quick_screen.yaml`，回执 artifacts.ip_quick_yaml 指向它；不要自己拼这个文件。明显撞车红灯停下换款/放弃，不能先把成本算完；用户确认具体款型。本步产物：market_md（`S1_选品板块/amazon-market-research/04_选款与对标.md`）、profile_yaml（`01_product_profile.yaml`，候选款写 product_options、对标写 competitor_asins.direct）、ip_quick_yaml（上面的快筛命令生成）。本步记录前插件会检查变体（product_variations）、旺季榜单（product_search_from_history）、自然前五（keyword_search_results）、广告关键词（product_traffic_terms）四项：调用完后运行 `scripts/capture_mcp.py --root "产品根" --step 4` 自动存回包（不要自拟文件名），再运行 `scripts/s1_market_facts.py "产品根"` 重算市场事实；工具不可用就存工具清单（`--inventory-file`）或报错回包作证据。没采也没证据的，本步不能记录。 给用户的候选款同时写进 `S1_选品板块/amazon-market-research/01_product_profile.yaml` 的 `product_options: [{code, name, benchmarks, …}]`；用户选款后用 `scripts/s1_choices.py --root "产品根" style --code <编号> --reply "<用户原话>" [--report <款型报告>]`（档案里没有候选表时加 `--name "<用户选中的款名>"`） 落档（写产品档案、在报告里写一次“本轮用户决定”），不要手改报告文字。
5. **1688 找货 + CT**：先做供应商对比，用户选定 1 家后才抓这一家的详情页和图片；本步不应长时间停留。**企业资料已给合作供应商时**（报价表等）：不搜 5 家择优，按 alibaba-supplier-evaluation 的「R09 合作供应商评估」逐家找到合作商自己的 1688 页面并抓取，证据写 `source_mode: user_specified_cooperator`；七维分由插件按页面信号自动算，不要写成 null。①**找 5 家**：装了 Sorftime（正常情况）就用 Sorftime 的 `ali1688_similar_product({search_name: 中文产品名})` 找货源，可加 `ali1688_product_search_from_image({image_url: 对标主图})`；某家要看文字详情用 `ali1688_product_request({product_id})`。不要用 `ali1688_product_search`：它只有类目/销量/价格筛选，没有关键词参数，搜不到本品。至少 5 家。没装 Sorftime 时才用 `1688_scraper.search_offers` 找候选。②**对比推荐**：按 alibaba-supplier-evaluation 的 7 维评分比较这 5 家，写 `02_1688供应商短名单.md`（候选全表、评分、为什么推荐第 1 家、备选），一次写完，停下等用户选 1 家。选定前不调用 `1688_scraper.get_offer` / `download_media`，不看任何商品图；文字里没有的规格（如尺寸能否容纳目标物）标「待看图 / 待厂家确认」。③**选定后**：只对用户选定的这一家用 `1688_scraper` 的 `get_offer` + `download_media` 抓详情页和全部图片，再逐张识别并做 CT（不只读main_04）。看图后发现这家不符合定位（如尺寸装不下），停下说明原因，请用户从短名单改选，不自动去抓其他家。识别回执按原图source、sha256、status、text/fields保存，失败写真实原因；没有视觉就明确失败/请求可用视觉或可读OCR，不谎称扫描完成。 用户选货源后用 `scripts/s1_choices.py --root "产品根" supplier --offer <1688编号> --reply "<用户原话>" [--sku <颜色/规格>]`：从已保存的 1688 页面 JSON 取价格档、起订量、件重尺（带 JSON 路径来源，页面提取≠厂家确认，已确认的值不覆盖），写进产品事实、供应商证据、产品档案并对齐定位；第 6 步成本模型会自动读到采购价、包装尺寸和重量。不要再现写脚本抠页面数据或往短名单末尾追加。

   先 `product_ct.py --run "产品根" --images-root "所选货源媒体根" --observation-template <临时文件.json>` 生成逐图识别回执模板（全部图片和 sha256 已列好），逐张看图后只改每项的 status / fields / text（字段名见模板里的 allowed_fields）；再 `product_ct.py --run "产品根" --init --images-root "所选货源媒体根" --image-observations <同一文件>`；已有CT则去掉--init。不用读 product_ct.py 源码找格式。CLI按实际图片清单核对SHA/重复/遗漏，不信complete:true。材质、规格、产品克重、单包类型/尺寸/毛重、箱规、价格、MOQ、资质、定制、配件风险逐项留source/status。产品克重不能直接充当含包装毛重。箱规体积容差5%、重量偏差15%、FBA/AWD普通外箱25in/50lb及尺寸边界10%提示自动核对；冲突仍保留，不改数字凑通过。厂家确认清单最多8问。

   用户选货源，facts.positioning记录实际形态/人群/核心词/尺寸/品类。与需求门定位比较：尺寸差异>30%、核心词或对标换品类、人群/形态变化任一满足就列变化，问「沿用原定位（换货源或定制） / 按新定位重新过需求门」。精铺E必须执行，不能把陶艺45×30cm静默换成通用五金71×35.5cm。第二种选择先展示并ack警示卡，再执行 `s1_flow.py "产品根" reopen-demand --user-message "用户本次实际定位选择原话"` 重开第3步，旧决定及历史事件保留；不能只写source:user脚本批准。

   页面已有价格、重量即继续第6步；包装尺寸已知则直接按页面算。厂家报价/交期/授权/箱规确认异步，不要求用户先说“后补”。只有价格或重量完全没有才硬停，未知字段null、场景边界和「页面数据，待厂家确认」如实保留。页面没有重量时，先用第 4 步已抓的对标 ASIN 包装重量（product_detail）取中位数作估算，写明来源和"估算，待厂家确认"，经用户认可后再记；不要随手取一个"保守上限"——重量超过 3 lb 会超出内置 FBA 费率表，后面整张成本账都会算不出来。不得为推进编造价格、毛重或采购授权。
6. **综合成本与定价**：先执行 `scripts/refresh_fx_snapshot.py --run "产品根"` 保证汇率快照在 24 小时内，再用 `skills/amazon-market-research/scripts/s1_cost_model.py --run "产品根" --init` 生成成本输入表 05_cost_inputs.yaml（顺序不可反；表里自带各字段说明）；调用唯一成本引擎；按页面数据先算，执行 `scripts/s1_margin_calculator.py open --root "产品根" --json` 自动打开正式毛利计算器并带入CT/成本输入。`quick --text "快算：采购33元，695g，36×20×4cm，卖24.99"` 可直接回毛利卡；`save --root "产品根" --input-json <UTF8.json|->` 存回，编辑格标user_attested，原未改格保留来源。目标价、竞品P25/P50/P75、费用与来源按标准六块输出。成本账不能整张是「—」：关税率按 HTS 编码查美国现行税率（含 301 等附加税），写进 `logistics.duty_rate` 并注明来源；查不到就请用户给一个税率，或用 `condition_scenarios` 分别按两个税率算出数字、标为条件结论。FBA 费超出内置费率表（单件超过 3 lb）时，用 Amazon 收入计算器或对标 ASIN 的 FBA 费填 `amazon.fba_fee` 并写来源。跑完看 `05_cost_model.yaml` 的 warnings，仍写着"实际利润待补"就补齐再 record，不要带着空成本账进入第 7 步。需要XLSX时显式导出，媒体与M1紧凑文件规则保留。 “要达到目标毛利，采购价最高多少、包装压到多薄”由成本模型原生给出（成本账里的“采购价与包装上限”一节）；需要别的厚度或售价档，写进 `05_cost_inputs.yaml` 的 `target_boundaries: {heights_cm: [...], prices: [...]}` 重跑即可，不要另写反推脚本或另出 05A/05B 报告。
7. **推广难度**：核心词月搜/CPC/来源日期、每售价的保本CPC和所需CVR、自然前5评论中位数、新品占比；给好推/有压力可测/难推一句话。转化率网格、各关键词每单广告成本与广告后利润、守住目标毛利的 CPC 上限都由 `s1_promotion_model.py --run` 原生算出（选了条件情景就按每套方案分别算），助手只需把核心词 CPC 和来源写进 `05_cost_inputs.yaml` 的 `ads.keywords`（格式 `[{keyword, search_volume, cpc, source: sif|xiyou|sellersprite|sorftime, core: true|false}]`）；需要单独的广告后目标时写 `target_post_ad_margin`。不要再现写分析脚本。
8. **IP与合规**：保留完整检索方法和原门禁。正式04A_compliance_ruler.yaml的summary_card固定商标/外观/发明/图片权属/合规声明五行，light+conclusion+needs_user+source，缺证据黄灯，不能用未查替代无侵权。红灯需要真实用户选换款/接受风险/放弃；仅接受风险可partial继续，并保留红灯与人工待核项。 原生顺序（R06.1）：①知识库用 `save_kb_evidence.py --step 8` 登记；②每查完一项必做检索，用 `skills/amazon-ip-risk-assessment/scripts/save_web_evidence.py --search <编号> --url … --result … --file <截图/页面文本>` 登记（自动存证据、标记尺子输入表已查；查不了用 `--status user_todo --reason`）；③在 `04A_ruler_inputs.yaml`（没有就先 `skills/amazon-ip-risk-assessment/scripts/compliance_ruler.py --run "产品根" --init` 生成）填属性判定与黑名单等业务判断；④运行 `compliance_ruler.py --run` 与 `sync_ip_report.py`。不要再手工复制截图、算哈希或改检索行。
9. **综合报告**：从结构化字段汇总唯一结论和七章正文，不复制子报告堆叠。活动入口仍为 sync_s1_decision_reports.py --compact-receipt，保留M1 MD+HTML+稳定09、不可变用户决定及完整原生字节/proof。真正验收失败交付警示卡和缺项，绝不写accepted或给下阶段口令。 原生顺序（R06.1）：①`scripts/s1_decision_prefill.py --root "产品根"` 用已有事实预填 `s1_decision_inputs.yaml`（产品名、目标毛利、货源链接与页面价、页面包装、合规研究灯色；已有内容不动）；②在 `01_product_profile.yaml` 的 `market_criteria` 写两项判断型判据 `strongest_counterargument`（最强反对理由）和 `pass_hold_stop`（做 / 暂缓 / 不做），格式 `{status: available, value, source: 证据相对路径, reason}`，其余八项由插件在生成综合报告时自动算出，不要手写；然后按 prefill 列出的 still_needed 补判断类字段（用量、需求证据与反证、厂家核查、风险是否排除、下一步），不知道就留 null：写进临时 yaml 后用 `s1_decision_prefill.py --root "产品根" --fill <文件>` 提交，不要直接改 `s1_decision_inputs.yaml`（已封存，直接改会报 physical source hash mismatch）；`01_product_profile.yaml` 的两项判据同理，用 `r01_native.py execute --step 9` 的 inputs 提交；③用户在本步指定的售价和采购方案写进 `05_cost_inputs.yaml` 的 `condition_scenarios` 并重跑成本模型；④运行 `sync_s1_decision_reports.py --compact-receipt`。不另写综合报告脚本。

独立01市场分析报告（R09）由插件生成：数字来自已存回包，判断写进 `S1_选品板块/amazon-market-research/market_narrative.yaml`（`scripts/s1_market_report.py template` 出骨架、`check` 查必填）。第3步必须取到目标节点 category_report 与 category_trend；第4步在 form_review 标出 10–20 个同款型并写读法、痛点、反向工程、SWOT、最强反方。不要手写或另起报告装分析；缺项由报告附录 A 列出缺什么、影响什么、怎么补。

## 更新与边界

厂家后补或计算器存回后，仅重算6成本、7推广、9报告，保留旧决定节点与8的有效IP证据；产品/定位/IP事实改变时按实际影响重新核验。旧accepted立即失效为pending，旧来源SHA失效不能放行。record/ack/导航沿用M1：只链接真实单步可读报告，业务原生文件通过CompactCase读取，raw不复制进state；步骤文本持久写集≤5，图片/视频不计，XLSX按需导出。

所有user_reply/decision仅来自实际用户输入；本模板和示例不是授权。旧案恢复、旧回填授权和原商业务门只在legacy.m1分支执行，不把旧第6步回填规则套到新第6步成本。
