# 20 · 旗舰版架构方案（基础版 + 星空广告终端）

适用：星空亚马逊 Bot Team 基础版 1.0.0-rc.12 起 · 2026-11-12
分支：`edition/flagship`（从 `main` 切出，不动 `main`）

## 一、结论

1. **两个版本，同一个仓库。** `main` 是基础版；`edition/flagship` 是旗舰版分支，包含基础版全部内容，再加广告终端的集成层。
2. **旗舰版 = 基础版（固定到某个版本）+ 终端模块。** 基础版有更新时，先合入 `main`，再单独发布基础版包；旗舰分支合入同一次更新后，单独发布旗舰包。两个包各自有版本号，不强绑定发布节奏。
3. **一个授权，多个版本能力。** 客户只需要一份旗舰包。买几套、几台机器，是授权数量的问题，不是下载次数的问题。
4. **终端源码不进 GitHub。** 广告终端源码留在本机（仓库外的同级目录），旗舰包在本机用 `build/` 脚本打出，分发方式另定。GitHub 上的旗舰分支只包含集成层：契约、校验、适配、授权字段、打包逻辑。
5. **终端是宿主的一个模块，不带模型。** 终端装进 AI 底座（OpenBot、StarSky，之后是 Grok Bot 等），由底座提供模型；终端自身不配模型密钥。
6. **第一阶段先做本机底座：OpenBot、StarSky（DSH）。** 它们与终端在同一台 Mac，文件夹契约直接读写，不需要同步。Grok Bot 运行在它自己的云电脑上，放到第二阶段，单独解决。

## 二、目录与分支

```
main（基础版）
└── edition/flagship（旗舰版集成层）
    starsky-amazon-botteam/
      adapters/{grokbot,openbot,starsky}   现有适配，保持不动
      handoff/                              新增：文件夹契约 + 校验脚本（两版共用）
      build/                                打包脚本：base / flagship / both（只含逻辑）
      license/授权接入规格.md               增加 edition / platforms / entitlements 字段
      docs/20_旗舰版架构方案.md             本文档

本机（不进 GitHub）
  /Volumes/Tool Disk/Grok Bot/StarSky Terminal（本地）/   广告终端源码
  构建时通过环境变量 TERMINAL_SRC 指向它，build/ 脚本不写死路径
```

## 三、文件夹契约（handoff）

数据落在本机用户目录，不在仓库内：`~/StarSky/handoff/`

```
handoff/
  manifest.json          版本、版本号、授权号、各文件 sha256
  outbox/                底座 → 终端（终端只读展示）
    products/*.json      选品、上架数据
    reports/*.md         运营日报等
  inbox/                 终端 → 底座（终端写方案，底座读回执）
    plans/*.json         待审核方案（只写方案，不推送）
    results/*.json       推送结果回执（由终端写入）
```

约定：
- 写文件用「先写临时文件，再 rename」，避免读到半截文件。
- 每个 JSON 带 `schema_version`、`source`（openbot / starsky / grokbot）、`created_at`。
- 谁写谁负责格式。终端只读 `outbox/`，底座只读 `inbox/results/`。
- 基础版不装终端也能正常写 `outbox/`，不报错。

## 四、授权字段

```yaml
edition: base | flagship
platforms: [grokbot, openbot, starsky]
entitlements: [terminal_ads, terminal_erp_youmai]
```

- 基础版只检查 `platforms`。
- 终端启动时检查 `entitlements` 里是否有 `terminal_*`。
- 纯本地校验可以被绕过。终端的真正价值在于接入店铺 API 和推送，这些需要客户自己的凭据，所以授权主要管交付范围，不用于防破解。

## 五、红线（沿用 01 号方案）

1. **凭据只在终端的本机密钥库里。** 底座不读、不转述 SP-API、Ads API、ERP 密钥。
2. **底座只出方案，不推送。** 底座把方案写进 `inbox/plans/`，不调用推送接口。
3. **推送只由老板本人在终端界面输入「确认推送」才执行。** 底座不能代为确认。
4. **底座调用终端走白名单命令。** 不给任意命令权限。
5. **基础版安装包不含终端代码、密钥和模型配置。**

## 六、阶段计划

**第一阶段：本机底座（OpenBot、StarSky）**
1. 写 `handoff/` 契约文档与 `manifest.json` 校验脚本，基础版先加。
2. OpenBot 写 `outbox/`，验证文件落地。
3. 终端加 `outbox/` 读取页面，用真实店铺数据跑通展示。
4. 终端加 `inbox/` 写入（方案上报），接审核报告与「确认推送」。
5. 授权加 `edition` 与 `entitlements`，打 base / flagship / both 三种包。
6. 用自己的店做一次全链路演示。

**第二阶段：Grok Bot（云电脑）**
三种方案，待定：
- A. 终端装到 Grok Bot 的云电脑上（需改动「密钥不进云电脑」红线，需明确改定）。
- B. 使用「Execution on this computer」，由 Grok Bot 在 Mac 上执行命令读数据（与 01 号方案一致，需实测）。
- C. 云端数据定时导出快照，同步到 Mac，终端在 Mac 上读（密钥不出 Mac，数据晚半天）。
