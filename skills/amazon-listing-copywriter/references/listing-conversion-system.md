# Listing 转化系统与自动化边界

## 目的

Listing 不是只承接流量的文案页，而是帮助系统识别产品、帮助买家完成购买判断的一组前台触点。本参考把这套判断拆成可交接的结构化产物；它不声称某一个字段、图片或算法变化必然提升排名或转化。

## 两类服务对象

| 服务对象 | 需要先回答的问题 | 主要落点 |
|---|---|---|
| 系统识别 | 卖的是什么、属于什么产品、关键属性是什么 | 标题、属性、结构化规格、关键词包 |
| 买家决策 | 是否适合我、能解决什么问题、为何可信、现在是否值得买 | Highlights、五点、图片、A+、Q&A、价格/配送/Review 等前台触点 |

文案 Skill 只对自己能控制的“事实、信息结构、图片交接、验证计划”负责。价格、促销、配送、库存、评论和关联模块由相应运营角色核查，不能被本 Skill 自动修改或假定为已优化。

## 工作顺序

1. **收集事实与需求**：从产品事实、关键词包、VOC、竞品结构和合规清单提取可写信息；区分已确认、条件性、AI 推断、禁止写入与待确认。
2. **建立买家问题表**：有VOC时优先引用真实来源；没有VOC可明确标为编辑拟题，不得冒充顾客原话。例如“是否适配”“怎样安装”“包装有什么”“是否适合某场景”，而不是为了凑五点而臆造。
3. **部署信息**：标题优先回答“你是谁”；Highlights 承接标题移出的增量事实；每条 Bullet 用“总 + 分”回答一个问题；属性、长描述、Q&A 和图片补足深层解释。
4. **生成视觉交接**：主图负责快速识别和点击前确认，副图每张只解释一个购买顾虑。文案 Skill 只给问题、证据、信息优先级和禁止表达；图片 Skill 仍须用本品垫图并遵守图片规则。
5. **创建验证计划**：对改版前后记录时间与可用数据，分别检查收录、曝光、CTR、CVR 和加购率。没有真实数据时只能写 `not_measured`，不能用“预计提升”代替结论。

## 五点“总 + 分”框架

- `Outcome`：这条为买家解决什么问题、带来什么可核验结果。
- `Feature`：哪些结构、材质、参数、配件或动作支持该结果。
- `Use Case`：在什么真实场景下、由谁使用，边界是什么。

不要用固定关键词次数或一句话模板取代判断。若某个结果没有产品事实支撑，将其放入审核区的待确认清单；消费者字段只保留已支持的事实与真实适配条件，不靠条件句加入未证实性能。

## 图片分工原则

| 图位 | 主要职责 | 不能做什么 |
|---|---|---|
| IMG01 主图 | 清晰识别本品、变体和售卖范围 | 叠字、用场景替代产品身份、表现非售卖配件 |
| IMG02–IMG07 副图 | 每张解释一个已排序的购买疑问 | 重复主图或用无证据的性能、认证、对比承诺填图 |

“手机端首屏可读性”是启发式审阅项，不是平台硬性截断规则。应输出实际首段预览供人工复核，而不是把某个固定字符位置宣称为官方标准。

## 验证与诊断边界

| 可见信号 | 优先核查 | 不能直接推断 |
|---|---|---|
| 曝光低 | 收录、关键词相关性、类目/属性完整性 | 仅凭文案就断定是竞争变强 |
| 曝光高、CTR 低 | 主图、标题首屏、价格、Review、配送展示 | 只改标题就能解决 |
| CTR 高、CVR 低 | 五点、图片、A+、产品匹配、竞品截流 | 只凭一个周期判断改版失败 |
| 加购高、CVR 低 | 价格、配送、促销、购买门槛 | 文案一定是根因 |

至少记录改动时间和观察窗口。适合做对照测试的元素，可使用真实用户或获授权的测试方法；不得伪造测试反馈、Review 或平台数据。

## 不应自动化成硬规则的说法

- “核心词一定要重复 N 次”；
- 评论权重、关联模块形成机制、配送阈值或 Canonical URL 改词的确定效果；
- AI 购物助手、OCR 或图片文字必然带来收录/推荐；
- 未验证的材质、续航、认证、兼容性、比较级和绝对化性能。

这些内容最多作为待核查假设、运营 handoff 或条件性建议，不能变成前台承诺。
