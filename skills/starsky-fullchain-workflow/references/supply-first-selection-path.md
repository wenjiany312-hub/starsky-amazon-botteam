# 有供应链的选品路径（supply_first）

> 建立：2026-07-28　依据：宠物用品实测暴露的步骤缺失
> 定位：这是 S1 的**第二条标准入口**，与「从零条件选品」并列，不是变体。

---

## 什么时候走这条

用户已经有**供应商 / 工厂 / 自有货源**，问题不是「做什么品」，
而是「**我这个供应商的一堆产品里，哪个能做**」。

这是大多数已有资源的卖家的真实起点 —— 比从零选品常见得多。

**触发信号**：用户提供了供应商目录、报价单、1688 店铺链接，或说「我有个合作工厂」。

---

## 八步，顺序不可调

```
① 供应商目录接入        → 结构化选品池（含重量/箱规/价格/限价）
② L0 供应可行性         → 规则筛，不用 MCP
③ L1 品类市场筛选       → Sorftime 拉数，品类级
④ ⛔ 品类内选款 → 定到 SKU   ← 实测缺失的一步
   ⏸ 停顿：把候选与理由摆给用户，**由用户拍板选哪个**
⑤ ⏸ 用户去 1688 店铺找选定产品的页面链接 → 投喂 → 抓取页面数据
⑥ L2 成本可行性         → 计费重 × 货代报价 → 允许到岸成本倒算
⑦ 市场穿透 + 竞品池     → 对**选定 SKU** 所在细分做深度分析
⑧ IP 侵权分析
⑨ S1 综合可行性报告（+ 唯一一份 HTML）
```

### ⛔ 实测踩过的错

2026-07-28 宠物用品：**③ 之后直接跳到 ⑥**，跳过了 ④。
结果 L3 输出「第 1 名：犬用雨衣（Raincoat）」—— 是**品类**不是产品。
用户看完报告不知道选了哪款、对应哪个 1688 链接，后续 S2/S3/S4 无法交接，
只能事后花 47 分钟打补丁。

**根因**：品类有市场 ≠ 这一款能做。同品类不同款的成本结构可能差数倍。

> 实例：该品类下两款雨衣
> 狗110 四脚连帽款 ¥50 / 377g / 抛重583g　　狗131 高领双腿款 ¥18 / 72g / 抛重208g
> **价格差 2.8 倍、重量差 5 倍** —— 两门完全不同的生意。

## 逐步要求

### ① 供应商目录接入

把报价单转成结构化选品池，**最少字段**：

`产品编号 · 产品名称 · 规格档 · 单件重量 · 包装尺寸 · 外箱数量 · 采购价（阶梯）· 平台限价`

缺「包装尺寸」时必须明写 —— **它决定抛重，抛重决定头程**，缺了后面全是下限估算。

同时抽出产品图（若报价单内嵌），**按锚定单元格反查出它属于哪个产品**，
用产品名命名存进 `供应商资料/产品图_按产品命名/`，并出一份 `产品图对照表.csv`
（产品名 · 大货价 · 图片文件）。

**两个用途，都很重要**：
- **⑤ 找 1688 链接时**：把选定产品的图直接摆给用户，他扫一眼店铺列表就认出来了
- **S3 出图时**：作为垫图候选

> 这些图通常是 1688 商品主图，**带中文营销叠字没关系** —— GPT-image-2 能处理干净。

本阶段**不看图内容**，只做提取与归位。

### ② L0 供应可行性（规则筛，不调 MCP）

剔除：无现货 / 需订做 / 有起订量门槛 / 本站点禁售。
**逐项报数**，并说明剔除理由。

> 这一步是纯规则，**应当用脚本预算好再进 AI**，不占现场时间。

### ③ L1 品类市场筛选

把保留产品**按品类归并**，逐个品类拉 Sorftime。

每品类一行：容量 / 增速或新品份额 / Top3集中度 / 价格带 / 判定。

**三条纪律**：
- Sorftime 返回的子类目与你归并的品类**不匹配时**，标「错配，待专门节点验证」，
  **不得借用不匹配的数据下结论**
- `Unavailable` 不当作 0
- 「新品份额」不是「增速」，两者不得混用

### ④ ⛔ 品类内选款 → 定到 SKU（本路径的核心步骤）

**品类选定后，若该品类下有 ≥2 款候选，必须逐款对比再定一款。**

对比维度（缺一不可）：

| 维度 | 为什么 |
|---|---|
| 采购价（大货价） | 直接成本 |
| **计费重 = max(实重, 体积÷6000)** | **决定头程；抛货品类差异极大** |
| **抛实比** | >1.5 说明是抛货，头程会显著高于按实重的估算 |
| 规格档数 | 档多 = 变体多 = 备货复杂度高 |
| 平台限价 | 供应商的售价下限约束 |
| 与目标价带的匹配度 | 能不能进那个价格带 |

**产出必须包含可下单信息**：

```yaml
product_code: ""          # 供应商目录里的编号，不是品类名
product_name: ""
supplier_offer_url: ""    # 1688 offer 级链接；没有则写"需向供应商索取"
offer_id: ""
selected_variant: ""      # 选定的具体规格档，不是"全系列"
purchase_price: ""        # 该档大货价 + 起订条件
chargeable_weight: ""     # 该档计费重
```

**缺任一项，本步判未完成，不得进入 ⑤。**


### ⑤ ⏸ 1688 产品页抓取（用户手工找链接）

**为什么要这一步**：供应商报价单给的是**目录级信息**（名称、规格、价格、箱规），
但缺**页面级事实** —— 材质细节、实拍图、SKU 变体、库存、供应商服务能力、买家评价。
这些要从 1688 商品页抓。

**为什么要用户手工找**：报价单通常只给店铺首页链接，不给每个产品的 offer 链接。
从店铺页面自动定位到"报价单里的狗131"需要浏览器操作 + 名称模糊匹配，
**慢、易错、且可能触发验证码**。

**正确做法**：

1. 告诉用户：**「已选定 XX，请到供应商店铺找到这个产品的页面，把链接发我」**
   同时给出四样，让他 30 秒就能认出来：
   - 店铺链接
   - 产品在报价单里的**名称与编号**
   - 规格与大货价
   - **⚡ 产品图路径**（`产品图_按产品命名/xxx.jpg`）—— **拿图去店铺认最快，比按名字翻快得多**
2. 用户贴回 `detail.1688.com/offer/{数字}.html` 形式的链接
3. 调 `1688-product-detail-scraper` 抓取
4. 抓到的页面事实与报价单**逐项比对**，冲突时按 `browser_offer_page > user_input` 优先级处理，
   并在报告中列出冲突项

**若用户拿不到链接**：写 `waiting_1688_offer_url`，标注哪些字段因此只能用报价单值，
**不阻断流程**，继续往下跑。

### 产品资料有三个来源，都要收进同一个目录

S3 出图与出视频只检索两个目录：**`00_产品资料/`**（用户与厂家提供的原件）和 **`S1_选品板块/1688-product-detail-scraper/媒体/`**（1688 抓取）。三个来源都要收进这两个目录：

| # | 来源 | 怎么来 | 标注 |
|---|---|---|---|
| 1 | **报价单内嵌图** | ① 步自动提取，按产品名归位到 `00_产品资料/报价单内嵌图/` | `source: 报价单` |
| 2 | **1688 页面抓取** | 本步 scraper 抓主图/详情图/视频，落 `S1_选品板块/1688-product-detail-scraper/媒体/` | `source: 1688页面` |
| 3 | **⭐ 厂家提供的成品图** | **直接问供应商要** —— 白底图、场景图、模特图、视频，放 `00_产品资料/厂家提供/` | `source: 厂家提供` |

**第 3 条最容易被忽略但价值最高。**

合作供应商手上通常已经有拍好的图 —— 白底、场景、甚至模特图和视频，
质量比 1688 商品页上那些压缩过的强得多。**开口要一句的事，很多人不问。**

**执行**：在本步提示用户 ——

> 「顺便问一下供应商有没有现成拍好的图片或视频（白底图、场景图、模特图都行），
> 有的话直接放进 `00_产品资料/厂家提供/`，S3 出图时优先用它们。」

拿到后建 `00_产品资料/来源清单.yaml`，逐文件记来源与可用性。
**S3 检索这个目录挑垫图时，优先级：厂家提供 > 1688抓取 > 报价单内嵌。**

> **这是演示的好素材**：它诚实地展示了「哪些事 AI 能做、哪些事人做更快」。
> 不要为了显得自动化而硬做 —— 让用户 30 秒复制个链接，比机器摸索 5 分钟强。

### ⑥ L2 成本可行性

用 ④ 定下的 SKU 与其计费重，配合**用户提供的货代报价**：

```
单件头程 = 计费重(kg) × 对应线路 ¥/kg
落地成本 = 采购价 + 单件头程
```

多家货代时逐条列出并选定一条作为基准，说明为什么选它（价格 / 时效 / 起运量）。

然后**倒算允许到岸成本上限**：

```
允许到岸成本 = 售价 − 平台佣金 − FBA − 单位广告成本
```

**⛔ 不得用采购价正算利润率。** 输出的是采购目标，不是利润预测。

对照：`落地成本` vs `允许到岸成本上限` → 差多少、能不能做。

### ⑦ 市场穿透 + 竞品池

**对象是 ④ 选定的那一款所在细分**，不是整个品类。

按 `amazon-market-research` 的证据级八条执行（属性注册表、交叉表、归一化单价、
新品成功/失败队列、Pass/Hold/Stop、最强反方、覆盖率降级）。

产出竞品池 → **这是停顿点**：用户拿 ASIN 去导词表、采视觉基准。

### ⑧ IP 侵权分析

**允许看图**，但限量：本品 1–2 张 + 竞品各 1 张主图，仅用于判外观相似度。

商标词、违规声明、外观相似度三线并行，产出可执行黑名单。

### ⑨ S1 综合可行性报告

整合 ①–⑧，给结论 + 最强反方 + 30/60/90 Gate。

## 与「从零条件选品」的差别

| | 从零条件选品 | **supply_first** |
|---|---|---|
| 起点 | 用户给条件（新手能做、非季节…） | **用户给供应商目录** |
| 选品逻辑 | 找市场 → 找货源 | **有货源 → 找哪个有市场** |
| 关键风险 | 找不到靠谱供应商 | **品类有市场但这款不行** |
| 核心步骤 | 市场机会挖掘 | **④ 品类内选款** |
| 成本数据 | 需要估 | **供应商目录直接给，可真算** |

**supply_first 的优势**：成本数据是真的，允许到岸成本倒算能算实。
**supply_first 的陷阱**：容易在品类层就停下，忘了还要选款。

---

## 现场演示价值

这条路径比「从零选品」更适合演示，原因：

1. **贴近真实处境** —— 大多数人有货源，缺的是判断
2. **数据是真的** —— 采购价、重量、箱规都是供应商给的，不用估
3. **④ 那一步天然有戏剧性** —— 品类选完以为结束了，一比款发现两个差 2.8 倍
4. **⑤ 抛重那一步能翻结论** —— 按实重算看着能做，按抛重算头程翻倍
