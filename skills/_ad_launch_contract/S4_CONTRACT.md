## 一句话

先用 S1–S3 资料判断，再跟用户把预算 / 毛利 ACOS / 能不能亏 / 打法谈清，然后出架构；用词库、Listing 埋词、主副图/A+ 和（有则调用）SIF 找新品机会词；**先出 HTML 新品广告报告，审过才出 Bulk**。3–5 天后用户把后台报表丢进指定目录，再出「阶段1优化」HTML；审过才出下一版 Bulk。

## 硬锁

1. **广告是 Listing 的放大器。** 标题、五点、A+ 里能写的词，才是首期该投的词。词库是来源，文案是过滤器，图片/A+ 是承接点。黑名单词（航空、承重、竞品品牌）文案不能写，广告也不能投。
2. **先判断，再交互，后出架构。** 标品/半标/非标、新品/成长必须根据已有资料写出来，不要开场就问。交互只问盘子：日预算、目标 ACOS（对照毛利/保本 ACOS）、前期能不能接受亏损、进攻还是控成本。
3. **HTML 在 Bulk 前。** 没有审过的新品广告 HTML + `architecture_review.yaml`，不准生成可上传表。HTML **必须**有专章「流量放大对照板」（见同目录 `流量放大对照板.md`）：每个主推词写清文案位置、图/A+ 承接、周 SV / ABA / CPC / 工具转化率、新品期动作。没有对照板，报告不算完成。
4. **SIF / 西柚 / 卖家精灵能抓就上板；广告知识库管方法，推广知识库管整品节奏。** 已有词包是底；有市场 MCP 再补当前窗口。分源记录，不混表。装了 `ads_knowledge_base` 时，第 2/3 步先抽短症状再 `kb_scenario_rules` / `kb_diagnose`，建议带 `KC-xxxx`。有 `promotion_knowledge_base` 时，断货重推/排名恢复/老品反超先调 `kb_scenario_rules(产品类型, 生命周期, 推广场景)` 取D0/D3/D7节奏，建议带 `PK-xxxx`，再定广告角色。知识库不是广告 API，不改出价。**外部数据接了就调（2026-10-25 用户定）**：第 2/4 步先看当前工具清单接了哪家（SIF / 西柚 / 卖家精灵），接了哪家调哪家，多家各调各的、分源记录，每家单步约 12 次以内，不出卡等批准；一家都没接就跳过，写一句“未接外部数据 MCP，用 S2 词库历史数据”。本地广告库/推广库不算“新增查询”，照常调用。上一阶段交接或口令里的“不新增查询”只管上一阶段，进 S4 不继承；用户在本阶段亲口说不查才不查。SIF 按实际有的工具依次：词根趋势 market_get_keyword_root_trend → 词根竞品 market_get_keyword_root_competitors → 单词需求/竞争 market_get_keyword_demand / market_get_keyword_competition → 机会筛选 market_screen_keyword_opportunities → 推广评估 market_assess_keyword_promotion；推广评估默认不传本品售价和利润率（宿主会拦截向第三方发送财务数据），盈亏在本地用 S1 成本算。SEO 在本报告里 = 词在 Title / Highlights / Bullet / A+ / 图的位置，不是另做一套站外 SEO。
5. **Bulk 前必须检查模板。** 插件内置 `AmazonAdvertisingBulksheetSellerTemplate.xlsx`（SHA `e1d85f4fcc571ac091ab5723cc31d4a60b89792b6a919a283303aa7800a36a7f`）必须在 Skill 根目录。用户若提供当前账户下载模板，优先用账户表。缺模板就停，不准手搓表头。
6. **系统不代传。** 审核通过 ≠ 已上传。有 Amazon Ads API 且用户明确授权时，才走预留的同步通道；默认永远是「出表 → 人传」。 <!--flagship-->
6. **系统不代传。** 审核通过 ≠ 已上传。永远是「出表 → 人传」。 <!--basic-->
7. **上传表只能由原生 `s4_launch.py sku` 出。** 没有真实 SKU 时停在第 6 步；用户要先看表，可以用本人确认的临时 Seller SKU 走同一命令出正式格式表，并在交付里写明“临时 SKU，上传前替换”。不出 DEMO 表冒充，也不用表格工具或临时脚本拼表；原生命令报错就停下，把原文给用户。
8. **上线后报表只认用户投喂的 Amazon 导出。** 路径：`S4_广告板块/_投喂_广告报表/`。第三方市场 CPC 不能冒充本账户 CVR。
9. **S4 读词库只走索引，不翻全量包。** 词库在 S2 已经定好（哪些词进哪个池、埋在 Listing 哪里、哪些否定），S4 只是照着投。第 1 步先刷新一次：
   `<python> <home>/skills/_keyword_system_contract/scripts/keyword_index.py --package S2_文案板块/<词库 Skill>/keyword_package.yaml`
   → 同目录 `ad_keyword_index.md`（人读：各投放池的词、周搜索 / ABA / CPC / CVR、Listing 位置、否定词）+ `ad_keyword_index.json`（几百 KB，写 brief 和对照板用）。
   查池 / 查词 / 否定词：同一脚本加 `--query --pool exact_p1`、`--query --words "a|b"`、`--query --negatives`（1 秒内）。
   ⛔ 不准写 `python -c "yaml.safe_load(open('keyword_package.yaml'))"` 之类的临时脚本翻全量包：它上万条记录、上百 MB，扩展名是 yaml、内容是 JSON，用 YAML 解析一次 80 秒以上。要全量字段就 `json.load`。
   投前核对索引里的「中文 / 未解释修饰词」：材质、款式、尺寸跟本品不符的词不投，写进对照板并回报 S2 修词包，不在 S4 手工改池子。

## 新案七步（R04）

当前流程、三个停顿、真实数据和续跑规则见 [当前广告执行](../starsky-fullchain-workflow/references/R04_当前广告执行.md)。权威步骤与路径为 templates/stage_roadmap.yaml，模型按当前宿主配置读取。

| 步 | 做什么 | 用户回答 |
|---:|---|---|
| 1 | 承接S1–S3、词库索引和00C | 不停 |
| 2 | 产品六问与类目/通用打法 | 不停 |
| 3 | 定预算、目标ACoS、损失和打法盘子 | 第一次 |
| 4 | 已许可词、实际图文承接、当前机会词和出价 | 不停 |
| 5 | 一页报告与一次方案批准 | 第二次 |
| 6 | 各变体Seller SKU填写、复述确认、原生出表与技术校验 | 第三次 |
| 7 | 广告组合四步上传指引、正常交接S5 | 不停 |

上架前不要求SKU/ASIN才能做方案。没SKU停在6；不能用演示表代替。ASIN可选，Seller SKU必填。已有批准不变时“填 SKU”“继续 S4”直接续第6步。审核数据结构保留，但架构批准与SKU确认分别生成对应记录，不多问一次。

首次上传四步：手动新建产品广告组合 → 上传Bulk活动及子项 → 核对结果 → 把活动加进广告组合。广告组是活动内部层级，不是广告组合；表不自动创建广告组合。

上线后的优化按既有S5手动报表路线，批量表放 `S5_运营板块/_投喂_广告报表/`，说“优化广告”。历史S4报表投喂路径仍只读兼容，不新增S5能力。

原九步仅用于保存原编号的旧案例；不得套到新案。新版报告不以50KB/12张表凑数，检查业务字段、当前来源、内容指纹和可读格式。上游未验收、视频待补、品牌跳过只在风险节汇总一次。
